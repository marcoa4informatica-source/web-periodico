## Mi recomendación directa

Para este proyecto **yo no haría WordPress**, pero tampoco haría un panel admin desde cero. Haría esto:

> **Frontend propio + CMS headless autohospedado + Docker bien montado.**

La opción que mejor encaja sería:

```text
Astro / Next.js
    ↓ consume API
Directus CMS
    ↓
PostgreSQL
    ↓
PDFs / imágenes en almacenamiento local o S3
    ↓
Docker Compose + Caddy/Nginx + backups
```

Mi opción preferida para tu caso: **Astro + Directus + PostgreSQL + Docker Compose + Caddy**.

Directus encaja especialmente bien porque te da un panel administrativo ya hecho, gestión de colecciones, subida de archivos, API REST/GraphQL y control de permisos sobre una base de datos SQL. Es decir: tú no tendrías que programar desde cero el típico panel para “añadir noticia”, “subir PDF”, “editar punto de venta”, etc. ([Documentación de Directus][1])

# 1. Punto importante: no necesitas “usuario” público

Tu idea de dos perfiles está bien pensada, pero yo la ajustaría:

| Rol                | ¿Necesita login? | Qué puede hacer                                                              |
| ------------------ | ---------------: | ---------------------------------------------------------------------------- |
| Visitante público  |               No | Ver noticias, ver secciones, descargar PDFs, ver mapa                        |
| Admin / editor     |               Sí | Crear, editar, eliminar noticias, ediciones, puntos de venta, redes, páginas |
| Superadmin técnico |               Sí | Gestionar usuarios, permisos, configuración sensible                         |

Para una web de periódico local, **el lector no debería registrarse** si solo va a leer y descargar PDFs. Es fricción innecesaria.

Directus permite que los datos sean privados por defecto y que tú configures qué colecciones puede leer el rol público sin autenticación. Eso te viene perfecto para exponer noticias publicadas, ediciones y puntos de venta sin abrir el panel admin. ([Documentación de Directus][2])

# 2. Arquitectura recomendada

## Opción recomendada

```text
[Usuario]
   ↓
[Web pública - Astro]
   ↓ API pública
[Directus CMS]
   ↓
[PostgreSQL]
   ↓
[Storage de PDFs e imágenes]

[Admin periódico]
   ↓
[Panel Directus /admin]
```

## Servicios en Docker

```text
docker-compose.yml
├── frontend        Astro / Next.js
├── cms             Directus
├── database        PostgreSQL
├── reverse-proxy   Caddy o Nginx
├── backups         servicio/cron de copias
└── optional        storage tipo MinIO si quieres simular S3
```

Docker Compose te permite definir todos esos contenedores, redes, variables y volúmenes en un único archivo `compose.yml`, lo cual es ideal para entregar el proyecto de forma reproducible. ([Docker Documentation][3])

Para el proxy, **Caddy** es muy cómodo porque puede gestionar HTTPS automático y actuar como reverse proxy delante del frontend y del panel CMS. ([Caddy Web Server][4])

# 3. Stack técnico que usaría

## Frontend

**Astro** sería muy buena opción porque esta web es principalmente de contenido: noticias, páginas estáticas, archivo de PDFs, mapa y secciones informativas. Astro está orientado precisamente a sitios de contenido rápidos y ligeros. ([Astro][5])

Usaría:

```text
Astro
Tailwind CSS o Bootstrap
TypeScript
Fetch a Directus API
SSR o generación estática según necesidad
```

También podrías usar **Next.js**, pero para este caso concreto puede ser más de lo necesario.

Mi elección:

```text
Astro > Next.js > React puro
```

---

## Backend / CMS

Usaría **Directus**.

Razones:

* Panel admin ya hecho.
* Gestión visual de colecciones.
* Subida de PDFs e imágenes.
* Roles y permisos.
* API automática.
* Base de datos SQL limpia.
* Buena opción para que editores no técnicos gestionen contenido.

Directus gestiona archivos mediante su sistema de ficheros y guarda metadatos en la colección interna `directus_files`, lo que encaja con las ediciones PDF y las imágenes de noticias. ([Documentación de Directus][6])

Alternativa posible: **Strapi**. También tiene Content Manager, Media Library y RBAC, pero para tu caso veo Directus más directo si quieres una estructura de base de datos clara y una administración tipo “tabla/colecciones”. ([Strapi 5 Docs][7])

# 7. WordPress vs Directus vs desarrollo propio

## WordPress

**Lo usaría solo si:**

* Presupuesto muy bajo.
* Quieren algo rápido.
* Les da igual depender de temas/plugins.
* No necesitan una estructura muy personalizada.

**Problema:** con el tiempo, WordPress puede convertirse en mantenimiento de plugins, actualizaciones, temas, seguridad y pequeñas chapuzas.

## Desarrollo propio completo

**Lo haría solo si:**

* Te pagan bien.
* Quieren algo muy a medida.
* Hay tiempo para mantenerlo.
* Vas a firmar mantenimiento mensual.

**Problema:** tendrías que hacer login, roles, CRUD, subida de PDFs, panel admin, validaciones, seguridad, recuperación de contraseña, editor visual, etc.

Para este proyecto me parece demasiado.

## Directus + frontend propio

**Es el punto medio ideal.**

Tú haces una web limpia, rápida y personalizada, pero el panel de gestión lo delegas en una herramienta profesional. Esa sería mi recomendación.

# 9. Docker Compose orientativo

Algo así:

```yaml
services:
  frontend:
    build: ./frontend
    restart: unless-stopped
    env_file: .env
    depends_on:
      - directus

  directus:
    image: directus/directus
    restart: unless-stopped
    ports:
      - "8055:8055"
    env_file: .env
    volumes:
      - directus_uploads:/directus/uploads
      - directus_extensions:/directus/extensions
    depends_on:
      - database

  database:
    image: postgres
    restart: unless-stopped
    env_file: .env
    volumes:
      - postgres_data:/var/lib/postgresql/data

  caddy:
    image: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./proxy/Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - frontend
      - directus

volumes:
  postgres_data:
  directus_uploads:
  directus_extensions:
  caddy_data:
  caddy_config:
```

Esto no es el archivo final de producción, pero sí la idea base.

# 11. Backups

Esto es clave. Un periódico va a subir PDFs y noticias. Si se pierde eso, hay problema.

Haría backup de:

```text
Base de datos PostgreSQL
PDFs subidos
Imágenes
.env cifrado o guardado aparte
Caddyfile
docker-compose.yml
```

Frecuencia recomendada:

```text
Diario: base de datos
Diario o semanal: uploads
Mensual: copia completa
```

Y dejaría documentado:

```text
Cómo hacer backup
Cómo restaurarlo
Dónde se guarda
Cada cuánto se rota
```

# 14. Mi decisión final

Para este caso concreto:

```text
Frontend: Astro
CMS: Directus
Base de datos: PostgreSQL
Mapa: Leaflet + OpenStreetMap
Proxy: Caddy
Deploy: VPS con Docker Compose
Backups: script automatizado
```

**No haría WordPress salvo que quieran lo más barato y rápido posible.**
**No haría todo desde cero salvo que te paguen mantenimiento y desarrollo a medida.**

Tu propuesta de Docker está bien, pero la clave sería esta:

> Docker sí, pero no para meter una app custom enorme innecesaria. Docker para empaquetar una arquitectura limpia: frontend + CMS + base de datos + proxy + backups.

Esa sería la forma más seria, mantenible y presentable para un periódico local.
